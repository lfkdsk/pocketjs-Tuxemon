# D2 deterministic day/night runtime

## Result

The imported game now has a saved, deterministic civil clock; live
`time_is` and `update_time` handlers; an independently seeded weather stream;
and named dawn/day/dusk/night tinting. The clock advances on active 60 Hz
reference ticks, pauses with the map world, and survives save/restore and
rewind. The implementation and its final validation are complete for the D2
scope.

Weather remains intentionally **Partial**: the ten source weather rows and a
deterministic deadline/RNG stream are present, but the source campaign does not
activate its weather-rules file. D2 therefore uses a deterministic 30–90 game
minute fallback schedule. Particle atlases, weather-driven battle modifiers,
and battle-entry time/weather snapshots remain later work.

## Runtime model

- `ClockState` stores Gregorian epoch day, minute of day, sub-minute reference
  ticks, total active-world reference ticks, and `ticksPerGameMinute`. The
  production default is 3,600 reference ticks per game minute, or one game
  minute per real minute at 60 Hz.
- A fresh interactive game samples local wall time once in the effect shell.
  Reducer and renderer code never read the wall clock. Tests, deterministic
  builds, QuickJS, browser verification, and journeys inject
  `2024-06-15 09:00`.
- The final map event is a terminal parallel ticker. It runs only while the map
  world runs, so absent host frames, transfer fades, fatal interpreter state,
  and default-frozen battles do not advance game time. Page `time_is`
  conditions project the ticker's one pending reference tick so page selection
  and the clock committed later in the same fold change on the same boundary.
- Runtime extension state uses a v2 packed string: the large immutable
  party/battle core is reused and only a flat clock/weather suffix changes on
  ordinary ticks. Disk saves retain the versioned v1 object codec. Saves made
  before clock/weather existed receive the fixed default; half-migrated saves
  with only one of the two fields are rejected rather than silently overwritten.
- Runtime validation requires `enteredAtTick <= clock.refTick` and
  `nextTransitionTick > clock.refTick`. This prevents a forged stale deadline
  from causing unbounded synchronous transition catch-up.

`time_is` follows all three upstream comparison paths:

- numeric comparison for hour, day-of-year, year, month, and day, including
  Python-style decimal/scientific `float()` spellings;
- exact equals/not-equals for weekday, leap-year, daytime, stage-of-day, and
  season;
- lexicographic `(month, day)` tuple comparison for date.

The upstream boundaries are preserved: daytime is 06:00–17:59; dawn 04–07,
morning 08–11, afternoon 12–15, dusk 16–19, and night 20–03. Gregorian leap
years, weekday, day-of-year, and both hemisphere season tables are derived from
saved state. `update_time` publishes the same eight string variables as the
source: `v.hour`, `v.day_of_year`, `v.year`, `v.weekday`, `v.leap_year`,
`v.daytime`, `v.stage_of_day`, and `v.season`.

The imported corpus contains 128 `time_is` conditions: 126 materialize as
native extension conditions and two belong to source events that do not
materialize. All three `update_time` source actions are also in non-materialized
events, but their live handler and a materializable fixture are covered by
tests. The current three calls all target `player`; character-local variable
banks for hypothetical NPC-targeted calls are not represented by the kit.

## Weather isolation

Weather stores its own slug, entered tick, next deadline, and Mulberry32
cursor. A transition consumes only that cursor and is anchored to the saved
deadline, so stepwise and batched folds agree and battle/session RNG is not
perturbed. The imported table has ten stable slugs.

The source tree does contain `mods/weather_previsions.yaml`, but the campaign
does not call `load_weather` or `set_weather`; the file also does not match the
current loader's expected wrapper/extension. Consequently the fallback is a
Pocket Tuxemon policy, not a claim that the upstream campaign currently cycles
weather. That distinction is why the status remains Partial.

## Daylight rendering

The visual grade uses the kit's named `screenTint` layer `tux.daylight`, so it
does not overwrite imported `set_layer` overlays. Five profiles cover dawn,
morning, afternoon, dusk, and night; transitions cross-fade for four seconds.
The extension publishes a target only at a stage boundary, and the built-in
screen-effect reducer performs the tween.

The committed Paper Town goldens were opened and inspected. The day image is a
normal, readable morning scene; the night image retains the same geometry and
sprites while becoming clearly darker and blue-shifted. Tests independently
decode the PNG pixels rather than trusting the manifest:

environment page disappears, both night pages appear, the environment becomes
`night_grass`, and the `tux.daylight` tint begins its 240-reference-tick tween.
Separate tests cover 60/30/20/4 Hz equality, fade and battle freezing, rewind,
midnight/leap-day rollover, weather deadline crossing, codec migration, and

## QuickJS cost

The desktop-host comparison used the same candidate benchmark binary for both
builds, a 480×272 viewport, the same 3,793-frame journey, thread CPU time, and
600 classified walking frames. Builds were measured in the order main → D2 →
D2 → main; the host load averages at launch were 8.27, 7.91, 8.40, and 8.47.
Thread CPU time avoids charging descheduling to a frame.

| Build/run | Walking QJS CPU mean | Walking QJS CPU p95 | All-frame QJS CPU mean |
| --- | ---: | ---: | ---: |
| main 1 (`b832794`) | 1.201 ms | 1.707 ms | 3.280 ms |
| D2 1 | 1.312 ms | 1.974 ms | 3.414 ms |
| D2 2 | 1.249 ms | 1.742 ms | 3.365 ms |
| main 2 (`b832794`) | 1.300 ms | 2.202 ms | 3.526 ms |

The pair means are 1.251 ms for main and 1.281 ms for D2: +0.030 ms per
walking frame, or +2.40% and 0.18% of a 16.67 ms frame budget. Across every
journey frame, including the battle workload, the pair means are 3.403 ms and
3.390 ms (-0.40%). Every measured frame remained below the host's 50 ms
QuickJS/core CPU guard. The clock therefore stays inside the component
repository's 3% performance regression yardstick in the walking slice.
