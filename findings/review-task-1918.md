## 4. Wiring deep-dive

a. **Menu → BattleRules**: `battle/runtime.ts:396-402` builds the root menu (`fight`/`item`/`capture`/`run`/`replacement`=swap only when legal), dispatch in `step()` (`:736-761`) routes each into `reduceBattle` with the right decision type; `itemEntries`/`swapEntries` (`:358-389`) enumerate one menu row per legal target, so double-battle Capture/Item/Swap correctly expose per-slot targets, not just a single implicit target. Confirmed.

b. **Persistence on battle end**: `battle/runtime.ts:500-546` (`completedExtension`) writes back inventory, `runAttempts`, capture insertion into party (≤6) then kennel (≤30), and `battle_last_result` via `enumCode(...)` (`:558-577`) from the reducer's `run`/`captured`/`won`/`lost`/`draw` result. Confirmed.

c. **Evolution + rewind codec**: `tux.check_evolution`/`tux.evolution`/`tux.cancel_evolution` (`battle/extension.ts:505-539,592-598,652-658`) manipulate `waitingToEvolve` on the party snapshot; the whole `TuxemonExtensionState` round-trips opaquely through `SessionState.ext` (`packTuxemonExtensionState`/`unpackRuntimeExtension`, `:172-181,300-301`), so a rewind/save restores pending-evolution state exactly. Independently confirmed live: `HZ=60 bun tools/smoke-spyder.ts` (win line) and `HZ=60 GB4_OUTCOME=lose bun tools/smoke-spyder.ts` both print `PASS L rewind crossed back into the active battle` / `PASS replaying after L rewind restores the identical result`, ending at frame 2788 (win) / 2893 (lose) exactly as `findings/GB3.md` claims, with post-merge canonical state sha256 `e47eb75642729ce7ed321f87a0ccce1f5c09b02a1d1a76cedb7c08e9cb3c7f98` — matching the hash the task context says the commander re-pinned after merging G8's shops in. Confirmed.

d. **BLOCKING — item-economy merge point is not actually reconciled.** The review spec specifically asks to verify "道具 add/sub 同时 ensureItem 与战斗库存 tux.change_item" behaves correctly after the merge. It only half does:
   - The **scripted** `add_item` event action does dual-write correctly: `importer/project.ts:1023-1036` emits both the generic `{op:"item", ...}` command (world-visible `SessionState.items`, via `ensureItem` for catalog metadata) **and**, when inside a battle-enabled map, `{op:"ext", call:"tux.change_item", ...}` (battle-authoritative `ext.inventory`, `battle/extension.ts:575-586`). This path is correct and is what the GB2/GB3 golden journey exercises (that's why the journey and 60,111-assertion test suite all stay green).
   - **Shop purchases/sales never reach `ext.inventory`.** G8's `itemShop()` (`importer/project.ts:849-867`) emits a plain `{op:"shop", ...}` command; the generic engine's shop-buy/sell handling (`vendor/pocket-rpgkit/src/engine/interpreter.ts:1607-1628`) mutates only `s.sw.items[row.item]` — there is no `tux.change_item` call anywhere in that path (confirmed by `grep -rn "tux.change_item"` across the repo: the only call sites are `add_item`'s importer emission and two test files).
   - **The reverse is also true**: `battle/runtime.ts:359-374` (`itemEntries`, which populates the in-battle Item/Capture menu) reads exclusively from `state.battle.inventory`, itself sourced only from `ext.inventory` (`battle/runtime.ts:689`); battle consumption (`tux.change_item`) never writes back to `s.items`. `ext.inventory` starts as `{}` (`battle/extension.ts:74-80`) and is mutated by nothing but `tux.change_item`.
   - **This is concretely reachable and severe**: all four imported item economies (`cotton_scoop`, `leather_scoop`, `tuxe_mart_taba`, `spyder_scoops` in `/var/tmp/tuxemon-src/mods/tuxemon/db/economy/*.yaml`) sell `potion`, `revive`, and `tuxeball` (repellent too, in `spyder_scoops`) — i.e., exactly the battle items and the primary capture device covered by GB3's own 216-capture-case / 25-item golden corpus. A player who buys a tuxeball or potion at any shop (e.g. the Cotton Mart quest the maintained journey's own NPC dialogue references — "bring me back some tuxeballs from the Cotton Mart") gets a `SessionState.items` credit that is invisible to the battle Item/Capture menu; conversely any item consumed in battle silently disappears from `ext.inventory` without decrementing the world-visible `s.items` count the shop's sell-back and `has_item` conditions read. The two "同一件事" bags diverge silently — no error, no test failure, because no test in the suite (including `tests/shop-import.test.ts`) buys an item and then checks battle inventory, and the maintained journey tape apparently never actually purchases from a shop before its one battle.
   - This is not caught by any of GB3's or G8's own gates, and it directly undermines "道具" (items/capture), one of the five features this review is scoped to. It also isn't declared anywhere as a known/accepted limitation (`findings/G8.md` documents the shop mechanics but says nothing about battle-inventory linkage).
