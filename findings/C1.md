## 1. GB5 确认键防护的测试缺口

`battle/runtime.ts` 的「确认键拒绝不可用指令」guard 删掉后测试仍全绿：游戏内光标永远不会停在

```ts
if (input.confirmEdge) {
  const index = Math.min(state.menuIndex, choices.length - 1);
  const selected = choices[index]!;

```

`tests/battle-runtime.test.ts` 新增 `ignores confirm on a disabled root-menu entry reached by
deserialized state`，直接构造两个「光标停在禁用项」的状态再按确认，断言整个状态 JSON 逐字节不变：

- 训练师战：根菜单 `menu[3]` 是 `{kind:"forfeit", available:false}`（reducer 无「对手认输」状态，
  恒禁用），把 `menuIndex` 改成 3 后按确认；

可用项）；其余 13 个测试全绿，证明只有这个反序列化场景触达该 guard。副本已删，原工作树 guard

### 3.2 为什么最慢

`buddha_mountain` 是全图最大的 100×100 = 10,000 格。地图文档 212,567 字节的构成：

| 字段 | 字节 | 占比 |
| --- | ---: | ---: |
| `ground`（10,000 个字符串） | 200,105 | 94.1% |
| `passage`（789 条稀疏覆盖） | 11,803 | 5.6% |
| 其余（events/sheets/id/尺寸） | ~660 | 0.3% |

而这 10,000 个 ground 字符串**只有 11 种唯一值**（`tuxemon-passage.0` 占 9,462 格，平均
17 字节/个）。read_parse 阶段 = `readFileSync`（分块 host 调用 + 信封 + base64 解码 + 拼接）
+ `decodeMapEntryBytes`（ASCII 解码）+ 整文档 `JSON.parse`
（`vendor/pocket-rpgkit/src/engine/map-repository.ts:407-419`）。

**read_parse 的去向（QuickJS 分段实测，21 reps 中位，详见 `findings/C1-fix1-readpath.md`）**：

| 阶段 | 中位 ms | 占 read_parse |
| --- | ---: | ---: |
| JS base64 解码（`base64ToBytes`，4 块） | 34.350 | 71.3% |
| JS ASCII 解码（`decodeMapEntryBytes`） | 12.018 | 24.9% |
| `JSON.parse`（整文档） | 1.382 | 2.9% |
| 其余（ABI 传输 + 信封解析 + 拼接，含宿主 handler） | 0.750 | 1.6% |

**瓶颈是 JS 侧两段逐字节循环——base64 解码（34 ms）与 ASCII 解码（12 ms）——不是
`JSON.parse`（1.4 ms，与评审对照的 1.564 ms 一致）**。宿主侧诊断量：整文件读盘 0.089 ms、
宿主 handler（盘读 + base64 编码 + 信封）0.339 ms、JS 侧观测传输 0.444 ms，合计不到 1.2 ms。
斜率：base64 0.1654 ms/KB、ASCII 0.0577 ms/KB、`JSON.parse` 0.0067 ms/KB、read_parse 全段
0.2323 ms/KB。validate/compile/commit 合计不到 4 ms，不是瓶颈。

这不是 buddha 独有现象：全 263 图 ground 唯一值中位数 2、p90 7、最大 16。ground 数组占文档
字节的比例中位 42.9%、p90 76.3%、max 97.8%（12/263 张 ≥90%；前列：water_cathedral 97.8%、
azure_town 95.5%、buddha_mountain 94.1%）——高占比集中在大图，小图 ground 占比低得多。

### 3.3 处置：游戏侧无便宜降法；组件仓紧凑编码 + PocketJS readText 补丁两条路

游戏侧两条可能的路都走不通：

- **导入产物**：地图文档形状由组件仓定义（`MapDef.ground: (string|null)[]`，
  `vendor/pocket-rpgkit/src/engine/types.ts:276`；`validateMapDefStructure` 强制 ground 为
  字符串数组，`map-repository.ts:235-246`），导入器按此形状产出；本任务被禁止改 `importer/`
  （另一任务在改），手改 `dist/` 产物会被下次 `bun run import` 覆盖且违反字节稳定门禁。
- **分片**：`splitProjectMaps` 已经是一图一分片；kit 的 map repository 协议（`mapIndex` 一条目
  一 `MapDef`）不支持把单图再拆，`tools/build.ts` 后处理也改变不了 kit 接受的编码。

**组件仓 + 导入器（不改引擎）**：给 `MapDef` 加紧凑 ground 编码——例如
`groundPalette: TileId[]` + `ground: number[]`（全图最多 16 种唯一值），或等价的打包字符串；
schema、`validateMapDefStructure`、compile 三处配套。评审 A/B 实测 `number[]` 紧凑 JSON 完整
文档 = **32,704 B**（不是 13–21 KB；13–21 KB 只可能对应另行设计的 nibble/RLE/二进制字符串
编码）。按 read_parse 斜率 0.2323 ms/KB 外推，buddha 文档 212,567 B → 32,704 B，read_parse
从 48.2 ms 降到 **~7.5 ms（−84%）**，余量从 0.3–7 ms 拉到 42+ ms。这是全图普遍受益（不是
buddha 专用）的改动；导入器侧的发射改动等组件仓落地后再跟。

**PocketJS 小补丁（走 PR）**：新增 `fs.readText` 类 op，宿主直接把文件字节做成 JS 字符串
返回（仍是 string-only ABI，sim/MCU 宿主可实现），一次跳过 base64 编解码、信封、拼接与 JS 侧
ASCII 解码共 7 段。buddha read_parse 48.2 → **~2 ms（−96%）**；所有文本文件受益，不只地图。
补丁范围（`contracts/spec/fs.ts` 新 op code、`pocket-fs` 实现、`framework/fs-api.ts`、各宿主、
测试）与备选 `fs.readInto`（套 `net.take` 的 ArrayBuffer 先例，−71%）见
`findings/C1-fix1-readpath.md` §5。

两者叠加：buddha read_parse → ~0.5 ms。
