# KB1 + KB2: extension commands, extension state, and battle scenes

Date: 2026-09-29

## Result

The component runtime now has generic, game-registered extension commands and
conditions, an opaque JSON extension slot, variable-addressed transfers, and a
pure Battle Processing scene lifecycle. No game-specific rules were added to
the engine. The only concrete battle implementation is the test fixture in
`tests/fixtures/toy-battle.ts`.

## KB1: extension boundary

- `src/engine/types.ts` defines recursive finite JSON, string-or-number
  variables, `{ op: "ext", call, args }`, `{ kind: "ext", call, args }`, and
  variable references for every transfer target field.
- `src/engine/extensions.ts` owns the registry and JSON boundary. Handler
  names must have a namespace such as `game.action`. Command handlers receive
  cloned arguments, read-only built-in banks, and a `random()` closure backed
  by the saved session mulberry32 cursor. Conditions cannot draw randomness.
  Returned extension state and variable writes are validated before commit.
- `createSession` scans all resident maps and lists every unregistered command
  or condition. A sharded map is checked when acquired. Preview tools must opt
  in to `allowUnknown: true`, which makes unknown commands no-ops and unknown
  conditions false.
- `SessionState.ext` defaults to `null`. It is cloned with reducer state,
  covered by checksums, encoded/decoded through an optional game codec, and
  checked by an optional game validator. An older v1 save with no `ext` member
  is hydrated as `null`.
- Transfer map, x, y, and direction values may be literals or
  `{ "variable": "id" }`; references resolve strictly against live variables
  when the command executes. Invalid live operands and unknown resolved maps
  enter a visible, frozen, non-saveable fatal content state rather than
  throwing out of `stepSession`.
- The project schema and the editor's embedded model accept and round-trip the
  new commands without a specialized editor form.

## KB2: Battle Processing and scene host

The game registers this pure interface through
`createSession(project, hz, { battle })`:

```ts
interface BattleRules {
  start(ext: JsonValue, setup: JsonValue, seed: number):
    { state: JsonValue; ext: JsonValue } | null;
  step(state: JsonValue, input: Readonly<BattleInput>, ticks: number): JsonValue;
  done(state: JsonValue): null | {
    ext: JsonValue;
    result: "win" | "lose" | "escape" | "draw";
    writes?: Readonly<Record<string, string | number>>;
    switches?: Readonly<Record<string, boolean>>;
    transfer?: BattleTransfer;
  };
}
```

`{ op: "battle", setup, onWin?, onLose?, onEscape? }` parks the owning fiber
in external mode. Entry consumes exactly one saved RNG draw and derives an
isolated u32 seed even when `start` returns `null`; a null start resumes the
fiber immediately. Otherwise the JSON battle state lives at
`SessionState.scene.state`. `step` runs once per host frame with fixed 60 Hz
reference ticks (`1/2/3/15` at `60/30/20/4 Hz`). On completion, the engine
validates the entire result, commits extension state and variable writes,
runs the matching branch, then performs an optional transfer. `draw` has no
branch.

Battle Processing requests are a persistent FIFO. The generic interpreter
keeps its established per-tick execution order: parallel fibers by stable key
first, then the main fiber. New battle requests are staged separately and
appended main first, then by parallel key, without changing same-tick
visibility for other commands. The head opens a scene. After a scene completes
and its fiber resumes, the next real scene opens on the next reference tick. A
`start()` result of `null` still consumes its RNG draw and resumes immediately
without occupying the scene slot. A stale request whose parallel fiber was
canceled is discarded rather than passed to game rules.

Scene-time behavior now follows the RPG Maker/Tuxemon world-freeze default:

- manual map input is zeroed and only the battle reducer receives buttons;
- map page sync, forced routes, NPC movement, fades, and every map interpreter
  fiber remain frozen;
- the battle-owning fiber remains parked;
- `GameView` hides the map and dialog tree, and mounts the registered scene
  component with only `{ state, width, height }`.

Games may explicitly pass `scene: { worldContinues: true }` to retain
background map simulation. Battle requests published in that mode still join
the FIFO and cannot replace or nest into the active scene. Callback return
shape violations remain programmer-contract errors; authored combinations of
events do not make `stepSession` throw.

The scene component cannot own authoritative mutable state. The scene JSON is
inside `SessionState`, so attract refolding and rewind reproduce any battle
frame. Active scenes and non-empty battle queues are not save points;
completion returns to a normal save point. Battle completion applies extension
state, variable `writes`, and boolean `switches` atomically before branching.

The toy fixture is a visible 1v1 ruleset with HP, seeded random damage,
win/lose/escape results, an optional faint transfer, and a 15-reference-tick
animation cursor.

## 修复 1（审查 1884 B1）

- Replaced the overwrite-prone single request slot with
  `InterpState.pendingBattles`. Same-tick requests are ordered main first and
  then parallel event key order; queued scenes run one by one and every live
  issuing fiber resumes. A successor scene starts on the reference tick after
  its predecessor completes, not recursively in the completion frame.
- Default scene policy now freezes page synchronization, movement, and map
  fibers while continuing only the absolute reference clock and battle
  reducer. The accumulated pause is applied to wait/text origins on completion,
  so frozen fibers stay byte-stable and their timers do not expire behind the
  scene. `scene.worldContinues: true` is the explicit compatibility opt-in.
- `canSave` independently rejects an active scene and a non-empty battle queue.
  Legacy v1 snapshots with `pendingBattle: null` hydrate to an empty queue.
- `BattleCompletion.switches` supplies atomic boolean switch write-back, so
  imported P1 battle-result switch conditions can remain unchanged.
- Regression coverage exercises two parallel requests in one tick, main versus
  parallel ordering, an in-scene request with background simulation enabled,
  the default full freeze, parallel-only save rejection, queue-gap and
  post-queue rewind, stable queued-battle hashes over two runs, and semantic
  equality at 60/30/20/4 Hz.

## 修复 2（复审）

- Restored the generic interpreter's original parallel-key-first, main-last
  execution order. Only battle requests emitted during the current tick are
  staged and reordered main-first before they are appended behind the
  persistent FIFO. A non-battle regression proves that main observes an
  earlier parallel write while parallel does not observe main's later write.
- Variable-addressed transfer operands no longer throw from `stepSession`.
  Unset/wrong-typed map, non-integer coordinates, invalid directions, and
  non-existent resolved map ids record `InterpState.error` with
  `kind: "content"`. Later frames freeze, saves are refused, and `GameView`
  displays the diagnostic. Registered extension/BattleRules return-shape
  failures remain explicitly documented programmer-contract assertions.
- A parallel 30-reference-tick wait spanning the default battle freeze now has
  a direct regression at 60/30/20/4 Hz: subtracting the host-quantized entry
  tick and frozen interval leaves exactly 30 ticks at every rate.
- Legacy v1 `pendingBattle: null` still hydrates to the empty queue. A
  populated old single-slot value is now directly tested and explicitly
  rejected by the normal non-empty-queue save-point invariant.

### `stepSession` exception audit

`rg -n 'throw new Error|throw error'` over the interpreter/session call-path
modules leaves three intentional categories:

- extension command/condition registration and return validation: registered
  game-code contract assertions, documented at the call sites;
- `BattleRules.start`/`step`/`done` and completion return validation, plus
  internal scene-slot invariants: registered game-code/engine assertions,
  documented at the call sites;
- project/session construction and known sharded-map acquisition integrity
  checks (schema, manifest, payload, checksum), plus `MapNotReadyError` as the
  UI's retry signal: setup/loading boundaries rather than event operand
  failures.

Literal or variable-authored transfer destinations are checked before map
acquisition. Thus no remaining `throw` in the audited fold is selected by an
ordinary event command, variable value, or built-in condition.

### Mutation checks

Two temporary mutations were applied separately and then reverted:

1. Replacing toy damage's saved-cursor draw with `Math.random()` made
   `bun test tests/battle.test.ts` fail `toy damage is independent of host
   randomness` and the branchability test: `8 pass, 2 fail`, exit 1.
2. Moving the toy RNG cursor into a module-level `hiddenRng` made the same
   command fail the deterministic/branchability sentinels: `8 pass, 2 fail`,
   exit 1.

Fix 1 added three more temporary mutations, each applied separately and then
restored:

3. Replacing FIFO append with a single-slot assignment made the focused battle
   suite report `13 pass, 4 fail`, catching lost same-tick work and broken
   queue replay.
4. Continuing the world by default made it report `16 pass, 1 fail`, with the
   freeze sentinel detecting map-fiber and NPC progress.
5. Removing the independent `scene === null` save guard made it report
   `16 pass, 1 fail`; the parallel-only active-battle save test is the failing
   sentinel.

Fix 2 added one more temporary mutation and restored it:

6. Reversing generic execution back to main-before-parallel made the dedicated
   non-battle visibility test fail (`0 pass, 1 fail`): `v.y` became `1` instead
   of remaining absent. Restored parallel-before-main then reported `1 pass,
   0 fail`.

After restoring the implementation, the focused battle file reports `18 pass,
0 fail`, and the full suite is green.
