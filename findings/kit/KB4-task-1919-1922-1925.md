# KB4 — battle UI kit: state-driven, rewindable, on-demand

Task: `fleet/task-1919`. Repo: `/var/tmp/oss/pocket-rpgkit` (worktree), baseline `main` = `fdc54ca`.
Scope: presentation only. KB1 (plugin commands/ext), KB2 (Battle Processing, `SessionState.scene`,
`GameView.battleScene`) and the toy `battle` command already existed at baseline — this task adds
nothing to the engine, only `src/ui/battle/`.

## What was built

`src/ui/battle/` — six exports plus a pure math module, all consumed through the new
`pocket-rpgkit/ui/battle` package export (kept **separate** from `pocket-rpgkit/ui`):

- `effects.ts` — `tweenAt`, `progress`, `windowDone`, `shakeOffsetX`, `flashOpacity`, `faintPose`,
  `frameIndexAt`, `barFillWidth`. Every function is `(descriptor, nowTick) -> number`, no clock, no
  Solid signal. `SpriteEffect { kind, startTick, duration }` and `Tween { from, to, startTick,
  duration }` are the two descriptor shapes a battle rules module writes into its own state.
- `StatBar` — HP/XP bar; fill width is `barFillWidth` (re-exported from `effects.ts`, not defined
  twice — see "JSX vs pure logic" below).
- `CommandGrid` — MV's 2×2 battle command grid, selected cell + per-cell `disabled`.
- `ListMenu` — scrolling skill/item/party list, reusing `ui/list-window.ts`'s `windowStart`/
  `truncateLabel` (the same scroll window DialogBox's choices/shop boxes use), with a title row and
  an optional description line.
- `MessageBand` — DialogBox's message-box typewriter, factored out as a standalone component (no
  choices/shop/portrait machinery).
- `SpriteSlot` — one battler image; position, horizontal shake, flash opacity and faint sink/fade
  are all `effects.ts` outputs.
- `FrameStrip` — a baked frame-strip effect (N pak images), frame chosen by `frameIndexAt`. **Not**
  a native auto-play sprite atlas: `AnimatedTiles.tsx`'s own comment explains why an atlas (cycled
  by the host's vblank clock) cannot carry state across a save/rewind, so a state-dependent effect
  has to swap discrete image keys the same way `PlayerSprite` chooses a walk pose.

## Demo: `tests/fixtures/kb4-battle/`

A second, richer `BattleRules` (`rules.ts`, `DemoBattleState`) than KB2's own
`tests/fixtures/toy-battle.ts` (deliberately not touched — KB2's tests pin its exact behaviour) and
a `BattleSceneComponent` (`scene.tsx`) built only from the KB4 primitives above. Flow: intro beat →
2×2 command grid (Fight/Skill/Guard/Run) → an optional skill submenu (3 rows, one `disabled`) →
instant damage + a shake+HP-tween beat → faint (sink+fade) → a separate win/lose message beat →
`BattleCompletion` with `writes`/`switches`. Damage/escape rolls use the session's own mulberry32
cursor (`engine/interpreter.ts:91` `rngNext`), matching KB2's determinism contract.

One finding worth flagging for whoever writes the real (Tuxemon) rules module: at the time this was
written, **`GameView`'s `useActions` only ever registered the `confirm` intent while a battle scene
was active** (its actions map fell back to `{ confirm: {...} }` whenever `modal()` was null,
`ui/GameView.tsx:484-499`), so `BattleInput.cancelEdge` (bound to the `back` intent / `BTN.CROSS`)
never fired during a battle. `up`/`down` edges bypassed this (`GameView` derives them straight from
the raw pressed mask, independent of the actions map) and so did any other raw-bit read a rules
module did itself. The demo's skill list "back" (BTN.CROSS) and command-grid left/right therefore
read `input.buttons` directly instead of trusting `cancelEdge`/a hypothetical
`leftEdge`/`rightEdge`. **Fixed in 修复 1 / B2 below** (`GameView` now registers `back` too; the
fixture reads `input.cancelEdge`) — left this paragraph as a record of the original gap rather than
rewriting history.

### B1 — `MessageBand` created/destroyed text nodes mid-performance

Root cause: `src/ui/battle/MessageBand.tsx`'s row and legend `Text` children rendered `""` for
"not yet typed"/"not yet complete", and solid-js/universal's `insertExpression` only patches an
existing text node in place (`replaceText`) when its *previous* value was already a non-empty
string — coming from `""` it tears the node down and creates a fresh one
(`node_modules/solid-js/universal/dist/dev.js`'s `current !== "" && typeof current === "string"`
branch). Every row's first typed character, every line-wrap boundary, and the legend's
reveal-complete flip toggled `"" <-> text` and so each cost one create+destroy+insert+remove.

Fix (`src/ui/battle/MessageBand.tsx`): both Text children now render a single space (`orBlank`)
instead of `""` whenever they would otherwise be empty — visually identical (a bare space glyph is
blank), but keeps `insertExpression`'s tracked "previous value" a non-empty string forever after
the first mount, so every subsequent frame takes the cheap `replaceText` path regardless of
whether the string is going blank or getting its first character.

Regression (`tests/kb4-battle-sim.test.ts`, "KB4 battle UI kit: determinism, Hz-independence,
steady state"): two new host-level tests replace the old one (which zeroed its counters one frame
late and only watched a 20-frame window, missing exactly the frames the review's QuickJS run
caught). Both now check **every single frame** from the beat's own mount onward — no window to
hide behind — and separately confirm the milestones the review named were actually reached:
- the hit beat (two-line message): first typed char, the row wrap, and legend completion.
- the faint beat: first typed char and legend completion.

QuickJS benchmark, now a committed, re-runnable script (`tools/kb4-quickjs-bench.sh` +
`tools/kb4-quickjs-bench.rs`, copied from the review's throwaway harness): boots the real desktop
`Runtime` against `dist/kb4-battle.{js,pak}` and counts `createNode`/`destroyNode`/`insertBefore`/
`removeChild` plus `Guest::frame`/`UiSurface::tick` timing. Rerun after the fix:

### B2 — a live `GameView` never delivered `cancelEdge` to a battle scene

Root cause: `useActions`'s closure in `src/ui/GameView.tsx` only ever registered `back` for a map
choices/shop modal; a game-owned scene (`scene() !== null`) fell through to the plain-talk
fallback branch (`confirm` only), so `BTN.CROSS` never produced `input.cancelEdge` for
`BattleRules.step`. This was flagged (not fixed) in this file's original "What was built" section
and the fixture had visibly worked around it by reading `BTN_CROSS` off the raw mask itself
(`tests/fixtures/kb4-battle/rules.ts`, "skills" phase).

Fix (`src/ui/GameView.tsx`, `useActions` closure): a `scene() !== null` branch now registers both
`confirm` and `back`, same shape as the shop-modal branch. `tests/fixtures/kb4-battle/rules.ts`'s
"skills" phase now reads `input.cancelEdge` like every other input path in the kit; the dead
`BTN_CROSS` constant is gone.

Regression (`tests/kb4-battle-sim.test.ts`, new "KB4 battle UI kit: scene input contract" describe):
drives an actual `GameView` (not a hand-built `SessionInput`) into the skill submenu, presses CROSS
through the real button pipeline, and asserts the scene reducer sees `phase: "command"` again —
proof `cancelEdge` reached it end to end, not just that the reducer *can* consume the field.

Side effect worth flagging: `GameView.tsx` is core, shared by every game (battle or not), so this

### B3 — the defeated side reappeared fully opaque during the win/lose message

Root cause: `tests/fixtures/kb4-battle/rules.ts`'s `step()` unconditionally reset
`effectSide`/`effectKind`/`tweenSide` to `"none"` at the top of every beat transition (so the NEXT
beat can own them), including the transition FROM the faint beat INTO the win/lose message beat.
`enemyEffect()`/`playerEffect()` had no memory of "this side is down" independent of "what is the
CURRENT beat's own effect", so the win message beat (whose own effect is legitimately `"none"` —
it's a message-only beat) made a fainted fighter's `SpriteEffect` read as `NONE_EFFECT`: full
opacity, rest position. `effects.ts`'s `faintPose` already held its terminal sunk/faded pose
correctly once `progress` clamped to 1 — the bug was rules.ts discarding the *descriptor*, not a
math error in the presentation layer.

Fix (`tests/fixtures/kb4-battle/rules.ts`): `DemoBattleState` gained `enemyFainted`/
`playerFainted: SpriteEffect | null`, captured (same `startTick`/`duration` the faint beat itself
used) the instant that beat starts, and never cleared for the rest of the fight.
`enemyEffect()`/`playerEffect()` now fall back to that captured descriptor whenever the current
beat isn't actively playing an effect on that side — `faintPose`'s own `progress` clamp does the
rest, so the settled pose (`sinkY` at max, `opacity` 0) holds through the win/lose message and
`done`, exactly as long as the scene stays up.

Regression: `tests/kb4-battle-sim.test.ts`'s new "the enemy stays in its settled faint pose (not
fully opaque) through the win message beat" scans the enemy's whole rest rectangle at the win beat
and asserts every sampled pixel is pure background, none are body colour. Golden: opened
`tests/goldens/kb4-battle.winmsg.png` after regenerating it — the enemy sprite is gone entirely
(compare `kb4-battle.faint.png`, mid-animation, where it's still partially visible/blue) — the
player sprite and "You win!" message are unaffected. Pinned FNV-1a hashes updated: 480×272
`winSettled` `72d5940a` → `f3757e0a`; 960×544 `winSettled` `a683a78a` → `236f918a`; every other
checkpoint at both resolutions (including `done`, since by then `BattleRules.done()` has already
completed and `GameView` has swapped back to the map — the battle scene isn't even mounted anymore)
is unchanged.
